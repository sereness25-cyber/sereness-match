# Phase 2-C いいね・マッチング・会話の実装計画

開始条件は [PR #7](https://github.com/sereness25-cyber/sereness-match/pull/7) の承認・統合。最新mainでその統合コミットを検証し、そこから専用ブランチと新しいPRを作る。今回の変更は計画と仕様書のみ。非本番の架空会員と実際のSupabase Auth・Data APIで検証する。

## 1. いいねと日次残数

- 男性フリーは1日5。男性プレミアム、女性、婚活サポートは1日20。基本枠の日付はDBの日本時間で決め、0時に新しい枠へ切り替え、繰り越さない。会員区分と権限をサーバー側から取得する。
- 通常いいねは1、メッセージ付きは3を消費する。ありがとうとスキップは0。追加枠の有効期限と消費順は未確定のため、今回の計画で固定しない。
- 送信RPCは実行者をセッションから特定し、双方の有効なアカウント状態と年齢確認、ブロック、自分宛て、重複、残数を検証する。本文・種別を検証し、残数更新と送信挿入を同一トランザクションに置く。
- `daily_like_balances` は会員・JST日付を一意にする。行ロックまたは残数条件付き更新で消費を直列化し、残数不足を拒否する。送信の一意制約と再試行IDで二重消費を防止し、同じIDで別の内容が送られた場合は拒否する。通信再送・日付境界を試験する。

## 2. 受信者の「ありがとう」

- 受信した有効ないいねを指定し、その受信者だけがありがとうを実行できる。対象の送信者・受信者をDBで取得し、双方の年齢確認・有効状態・ブロックを再検証する。返答処理で残数は消費しない。
- 送信者・第三者からの返答、存在しない対象、無効になった対象を拒否する。再送時は同じ結果に収束させる。互いに通常いいねを送っても成立させない。

## 3. マッチング成立

- ありがとうの受理と、ペアに一意な `matches`、`conversations`、`conversation_members` の作成を一つのトランザクションで行う。片方だけ保存される状態を残さない。旧PR #2の相互いいねによる自動成立は移植しない。
- 同じペアの成立・ブロックで同じ順序のペアロックを使い、成立直前に条件を確認する。二重クリック・再試行・双方同時のありがとうでも同じペアの会話は一つだけ。失敗時にいいね受理・会話の一部を残さない。

## 4. 成立者だけが利用できる会話

- 参加者だけが許可された会話とテキストメッセージを閲覧・送信できる。RLSと送信RPCで参加、成立の有効性、双方の年齢・有効状態、ブロックを検証する。送信者はサーバーで確定し、直接挿入や会話外の読み取りを拒否する。
- 既読・写真・通報担当の閲覧は別権限として扱う。Realtimeを追加する際は、参加者以外にイベントが配信されないことも確認する。

## 5. ブロック・通報・証拠保持

- ブロックの更新と交流系RPCが同じペアのロックを共有するようにし、双方の新規交流と対象の閲覧を制限する。解除は過去の成立を自動復元しない。
- 会話の利用停止と、通報に必要な証拠の保存を分ける。ブロック時に会話行を削除する旧方式は採用しない。証拠は関係者に無条件公開せず、担当権限・理由・監査・保存期間を設計してから運用する。保存期間・解除後の履歴表示範囲は運営判断まで保留する。

## 受入テスト

| 範囲 | SQLと認証付きAPIで確認する条件 |
|---|---|
| 残数 | 四区分の5／20、消費1／3／0、JST日付切替。残り1への並行送信、同一リクエストの再送、ロールバックで過消費がない |
| 権限 | 匿名、第三者、自己宛て、年齢未確認の双方どちらか、利用停止の双方どちらか、相互方向のブロック、送信・返答の重複を拒否 |
| 成立と会話 | 通常いいね2件では成立なし。受信者のありがとうだけで成立し、同時要求でも会話は一つ。未成立・第三者の読取・直接書込を拒否 |
| 安全性 | ブロックとsend/成立の同時操作を検証。制限後に新規メッセージを作らず、通報証拠と監査行を保持。解除で成立・会話権限を戻さない |
| 回帰 | Phase 2-A/BのAuth・RLS、デモ・Pages向けビルド・オフライン再読み込みを維持 |
