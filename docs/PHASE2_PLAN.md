# Phase 2 最初の作業計画

作成日 2026-11-28（JST）。対象は使い捨てのローカルSupabaseまたは開発専用プロジェクト。今回のPRには実行計画のみを含める。Phase 2全体の完了条件は [DEVELOPMENT.md §9](../DEVELOPMENT.md) を参照する。

## 1. 接続先と秘密管理

1. 次の作業ブランチはPhase 1の承認済み基点から切る。ホストにDockerがない場合は、[PR #2の既往CI](https://github.com/sereness25-cyber/sereness-match/pull/2) と同様にGitHub Actions上の使い捨てローカルSupabaseを使う。プランやアカウントの新規契約はこの手順に含めない。
2. 本番と開発の接続先を識別し、起動前に開発側のプロジェクト識別子またはループバックURLを照合する。URL・公開キー・Authリダイレクトを開発用に限定する。メール認証の検証にはローカルのメール捕捉機能を用い、架空データを本番へ送らない。
3. Phase 1は `VITE_SUPABASE_PUBLIC_KEY`、DATABASE.md §38は `VITE_SUPABASE_PUBLISHABLE_KEY` を記載している。Phase 2の実装で仕様名に揃え、環境変数例・検証・CIを同時更新する。ローカルスタックから得た公開用キーをブラウザに渡し、サーバー資格情報を必要とする検証はテストプロセスに限定する。
4. デモの `sereness-v04` を移行元に使わない。接続設定が欠落・不正の場合は起動設定のエラーとして表示する。開発用接続の成否はレスポンスと権限で判定する。

## 2. マイグレーションの順序

| 作業単位 | 内容・成果物 | 検証 |
|---|---|---|
| P2-A 接続 | CLIバージョンを固定。ローカル用設定、架空seed、環境変数例、読み取り専用の接続確認 | 接続先とAuthを確認。公開キー・未認証の状態で非公開データが見えない |
| P2-B 最小スキーマ | アカウント、非公開情報、役割／権限、プロフィール、審査状態から追加。FK、一意制約、必要なインデックス、既定拒否のRLSを同時に定義 | 空のローカルDBへ適用。架空seedを登録後、本人と他会員で読めるデータが異なる。停止会員も検証 |
| P2-C 会員間の最小モデル | 旧PRの `match_likes`、`match_pairs`、`match_messages`、`match_blocks` を、仕様の likes、matches、conversations、conversation_members、messages、blocks に対応付ける。安全条件・監査・通報証拠の保持を設計してからSQL/RPCを再利用 | 双方の年齢、ありがとう、参加者、ブロック、直接書込拒否、一意性を確認。旧PRの即時相互成立・会話削除はそのまま採用しない |
| P2-D 非公開Storage・運営 | DBポリシーとStorageの両方で所有者・目的別の権限を設定。審査書類の公開制限、短時間の閲覧権限、役割別の監査を検証 | 架空ファイルを使い、他会員・停止会員・担当外管理者による読取と署名URL取得を拒否する |
| P2-E 拡張 | DATABASE.md §37の順序で、残りの設定、足あと、お気に入り、決済・ポイント、店舗・イベント、相談等を小PRに分ける | 依存関係と受入テストを機能別に定義。今回の最初の作業では実課金・本番データを対象に含めない |

新規マイグレーションをファイル化し、クリーン適用と通常の前進適用を別々に確認する。ローカルの使い捨てDBでのみ `supabase db reset --local` を使う。DBテストにはロール別のSQLアサーション、統合テストにはAuthとData API経由の認証付きリクエストを使う。 [Supabase CLIのリセット仕様](https://supabase.com/docs/reference/cli/supabase-db-reset) · [RLS公式ガイド](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 3. RLSの判定表

| ケース | 許可する操作 | 拒否・非表示を確認する操作 |
|---|---|---|
| 匿名／メール未確認 | Authの登録・確認フローの範囲 | 一般会員プロフィール、非公開列、全ての会員間書込 |
| 確認済みの会員A／B | 本人編集と、Bが公開した許可項目の閲覧 | 他者更新、非公開情報・非公開写真、自己への審査承認や役割付与 |
| 年齢未確認／片側のみ確認 | 仕様が許す編集・閲覧 | いいね・ありがとう・成立・会話書込。プラン権限があっても拒否 |
| 双方の年齢確認／本人確認なし | 有効会員が双方合意し成立した後の許可範囲 | 未成立時の会話、第三者の読取、直接挿入、重複操作。本人確認は必須にしない |
| ブロック／停止 | 本人に許されたブロック管理、担当者の監査 | 双方向の検索・交流、停止会員の古いセッション、証拠の無断削除 |
| 管理者／審査担当 | 担当範囲の審査、理由付きで許された閲覧 | 担当外の書類や会話、会計・監査権限の越境、一般会員からの管理操作 |

許可ケースは期待行と期待列まで照合する。拒否ケースはエラーか空結果を操作ごとに定め、DBへの副作用がないことを確認する。SQLとHTTPの両方で確認し、サーバー専用の権限で得た結果は一般会員の合格証跡に使わない。試験結果には環境種別、コミット、マイグレーションID、期待値、実結果、CIのリンクを記録する。

## 4. 開始と完了の判定

最初の作業の開始には、Phase 1の承認済み基点、開発用の接続先、使い捨てDB・架空データ、P2-A/P2-Bの受入条件をそろえる。本番URL・本番SMTP・本番マイグレーションは別の変更として扱う。

最初の作業は、接続・空DBからの適用・架空データの読み書き・最低限の権限拒否が再現でき、Phase 1回帰が通れば完了。Phase 2全体は残りのテーブルと権限まで検証して判定する。次のPRで実施し、正式公開の可否とは別に報告する。
